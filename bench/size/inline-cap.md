# Inline expansion cap — how the default was chosen

`INLINE_MAX_NODES` (`src/compiler/codegen.ts`) bounds how much one emitted function may
grow by pasting single-use ref bodies into it. This file records the measurement the
default came from, so the number can be re-derived rather than re-argued.

## What is being capped (and what is not)

Two different mechanisms get confused with each other. Only the first is capped.

- **Single-use ref inlining.** `emitLazy` pastes the body of a ref that is used exactly
  once and is not recursive, rather than hoisting a function nobody else calls. Correct
  per ref, unbounded in aggregate. **This is what the cap bounds.**
- **Identity-keyed hoisting of a multiply-referenced subtree** (`HOIST_MIN_SUBTREE`).
  Already works and is not a growth source: a shared object referenced 1 or 38 times
  emits flat. The cap does not touch it.

A rule-map entry is never inlined either way — it has to stay an addressable
`_r_<Name>` — so the cap can only ever act on a private `ref()`.

## Measurement

Sweep of `PARSEMAN_MAX_INLINE` over `examples/css/parser.ts`, the largest in-repo
grammar (247,553 generated bytes). `cappedSites` counts refs that became calls;
`maxNodes` is the largest single body the cap turned away.

| cap | generated bytes | capped sites | capped nodes | largest body |
| --- | --- | --- | --- | --- |
| off / 4000 / 2000 / 1000 / 500 / 250 / 100 / 50 | 247,553 | 0 | 0 | — |
| 25 | 245,066 | 3 | 26 | 14 |
| 10 | 243,010 | 7 | 72 | 16 |
| 5 | 242,750 | 11 | 95 | 16 |
| 2 | 242,251 | 12 | 98 | 16 |
| 1 | 242,202 | 12 | 99 | 16 |

Across the whole `bench/size` probe suite (21 fixtures) the same instrumentation at
`cap=0` records **zero** inline sites: those grammars are rule-map only, so nothing is
eligible.

## What the numbers say

1. **The largest single-use body anywhere in the corpus is 16 combinator nodes**, and
   the busiest single function absorbs 99 in total.
2. **Single-use inlining is not the size driver.** Turning it off completely buys 2.2%
   on one fixture and nothing anywhere else. The driver is per-`node()` emission
   (~5,230 bytes per site, flat across an 8x range), which no inlining policy reaches.

## The default: 1000

Chosen to sit roughly 10x above the busiest observed function (99 nodes) and 60x above
the largest observed single body (16). Consequences, both verified:

- **It does not bind on any grammar in the repo**, so emitted output is byte-identical
  to the uncapped compiler and the perf risk of the cap is not "small" but *zero* —
  there is no code change to measure. `pnpm size:guard` reports identical bytes with
  the cap present and with `PARSEMAN_MAX_INLINE=off`.
- **It still bounds the pathological case** — a generated or machine-authored grammar
  with a deep chain of single-use helpers — which is the only case where this
  expansion has ever been unbounded.

A tighter default was rejected: below ~50 it starts converting real bodies to calls in
`examples/css` in exchange for tenths of a percent, which trades the product's headline
property (macro mode does not pay call overhead) for bytes that are not where the
problem is.

## Escape hatch

Off by default, explicit when used:

- `compile(g, { maxInline })`, `compileRuleMap(map, { maxInline })`,
  `compileLinkable(map, ns, { maxInline })`
- `PARSEMAN_MAX_INLINE=<n>`, or `off` / `infinity` to disable the cap entirely

## Re-deriving the table

The sweep is a dozen lines against `compile()` plus `beginInlineCapCapture()` /
`endInlineCapCapture()`; it is not committed as a script because it runs once per
policy change, not per commit. `test/unit/inline-cap.test.ts` is what runs per commit,
and it pins the properties the table cannot: identical parse results when the cap
binds, byte-identical source for the same grammar and cap, and that the cap is visible
when it acts.
